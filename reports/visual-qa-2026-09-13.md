## Why this axis and not the usual sweep

The CSS/JS delta since the 09-10 baseline is still **zero bytes**, and the
chrome axes were measured clean this morning on a 122-page delta+control
sample. Re-running them is churn.

What was *not* closed is the thing that sample could not settle. The 09-13 note
says it plainly: the grouped-variance pass found `.related-card-link` drift on
**one** page of the 122, while the corpus actually had **26**. Finding a defect
class on a sample and quoting the sample's count is the recurring failure here.
So today's run is the full-corpus enumeration of that same axis: **all 755
pages**, per-page, one computed-style bucket per component.

Per-page (not cross-page) is the right unit. It is family-safe — a printable and
an article may legitimately style the same class differently, so cross-page
bucketing would report every template boundary as drift — and it still sees the
09-13 defect, which was 1–3 links diverging from siblings *inside one grid*.

## Probe

Three exemptions carried verbatim from the 09-13 note (region-scope the class
key; strip `.wwk-navlist` + `active`; exempt `.mobile-bottom-nav`'s 10px
labels). Colours bucketed at **1280** — `m-app.css !important` masks colour
drift at ≤768, so a mobile bucket cannot fail.

The canary needed two further rounds, both of which are probe bugs worth
keeping:

1. **Region must be the ancestor CHAIN, not the nearest match.** A page can
   carry two `.hero-actions` blocks — one in the dark `.page-hero`, one in a
   light `.sidebar-card` — and they theme differently *and correctly*.
   Nearest-only collapsed them to one key and the clean control page reported
   drift against itself. Key is now `.page-hero>.hero-actions::A.button`.
2. **State elements must be excluded from the buckets, not just stripped from
   the key.** Stripping `active` (exemption 2) keeps identity stable but then
   makes the single selected filter chip an odd-one-out against its inactive
   siblings — education hub showed 1 active + 94 grey `.cat-btn`, home 1 + 6
   `.mobile-cat-item`. Both are the named design-intent FP.

**Canary gate:** true-negative page reports 0 multi-bucket AND a true-positive
copy catches both an injected sibling divergence and an injected chrome rule,
asserted at 1280 and 390. Passed on 3 pages across 3 template families.

## Worth Michael's attention

**1. `.hub-answer` has no CSS rule at all.** The section-vs-FAQ size difference
is real design intent, but it is encoded as the same inline
`style="font-size:0.98rem;"` repeated **17 times** across 4 hub pages, with
nothing in any stylesheet. It is consistent today. It is also exactly the shape
that produced the 09-13 `.related-card-link` defect — same class shipping in a
bare and a styled form, both clearing every floor, so no threshold probe can
see it. One FAQ answer added without the inline style renders a notch too large
and nothing catches it. A class (`.hub-faq .hub-answer`) would make the
distinction intentional and drift-proof. Not done here: it touches 4 files plus
a stylesheet, and a CSS change forces a sitewide cache-bust bump — more blast
radius than a zero-visual-change refactor earns without a call.

**2. `.content-grid` 30px step — reconfirmed, still open.** The keyword-hub
screenshot shows body text at x≈114 while the header logo sits at x≈84 at 1280,
matching the 09-07 finding exactly. Still 122 pages, still a typography call
(the fix widens the reading column by 48px and reflows all of them).
